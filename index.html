Featured project

Production Line Defect Data Digitization Platform

Power Apps (Canvas) · Power Fx · SharePoint Online · iPad — automotive manufacturing · Role: Lead developer & system designer

Overview

On the assembly line, parts pulled out for a quality concern were tracked entirely on paper. A defect was written on a slip, walked to the repair area, fixed, checked and filed — which meant no real-time visibility, no reliable link between a defect and its repair record, handwriting-dependent data quality, and days of manual effort before anyone could analyze trends.

I designed and built a tablet application that replaces the paper slip with a single traceable digital record. Each part is registered once at the moment it is pulled from the line, then carried through every downstream step by a unique tracking ID, so the defect report, the repair work, the verification results and the final quality judgement all resolve to one record that can be queried instantly.

What I designed & built

  • Staged workflow engine. A status-code state machine advances each record through five sequential stages. Every screen validates the record's current stage before allowing input, so steps cannot be skipped, duplicated or completed out of order.
  • Master-data-driven input. Operators select from centrally managed master lists rather than typing free text — defect categories, cause classifications, process locations and personnel are all governed centrally, keeping the captured data clean and analysis-ready.
  • Barcode-first UX. Scanning the part label populates identity fields automatically and routes the operator straight to the correct next step, minimizing typing with gloves on a noisy line.
  • Photographic evidence capture. Built-in camera steps attach before/after images to the record, giving quality engineers visual context that paper never provided.
  • Role-aware accountability. Reporter, repairer and inspector are captured as distinct roles at each stage, with a fast in-app operator switch designed for shared shop-floor tablets.
  • Review & search layer. A dedicated set of screens lets supervisors filter historical records by period, line and category to review what happened without touching the raw data store.
  • Reliability by design. Confirmation dialogs before every commit, transactional multi-record writes, and input validation with plain-language error messages — designed so a mis-tap never corrupts a traceable record.

Scale & engineering approach

The delivered application spans roughly 45 screens and 20,000+ lines of Power Fx, backed by 30+ structured data entities split between governed master data and transactional records. To keep a codebase that size maintainable, I standardized a small set of reusable interaction patterns — paginated selection dialogs, the photo-capture step, the confirm-then-commit save routine and shared validation logic — and applied them consistently across every stage. I also authored full Japanese technical documentation so the in-house team could own the system after handover.

Outcome

Real timeStatus visible while work is in progress
End-to-endTraceability from defect to disposition
In-houseBuilt internally, avoiding vendor cost

Beyond the paperwork saved, the real gain was analytical: quality trends that previously required manual tallying became a query, giving engineers the evidence base to target recurring defects at the source.

Cloud Data Platform

SAP-to-Lake Metadata-Driven Pipeline Framework

Reusable Azure Data Factory framework that extracts SAP and internal system data through CDS views, transforms it into report-ready datasets and lands it in ADLS Gen2. Sources, tables and mappings are declared as metadata rather than hardcoded into pipelines — so onboarding a new source became a configuration entry instead of a development cycle, cutting onboarding time by up to 60% while handling up to a million rows per run.

SAP CDS Views Azure Data Factory V2 ADLS Gen2 Metadata-driven design

The problem

The data the business needed for reporting lived inside SAP and other internal systems, where it is structured for transactions rather than analysis. Every new reporting requirement turned into its own extraction job with source names, table names and mappings written directly into the pipeline — meaning more pipelines to maintain, duplicated logic, and a development cycle standing between a question and its answer.

End-to-end data flow
SAP & internal systemsSystems of record
→
CDS viewsSemantic extraction layer
→
Azure Data Factory V2Scheduled extraction
→
TransformationReport-ready shaping
→
ADLS Gen2Governed lake storage
→
Power BIReports & dashboards for the business

How the pipeline works

  • 1Expose at source via CDS viewsRather than reading raw SAP tables, extraction runs against CDS views — the joins, filters and business meaning are resolved at the source, so what leaves the system is already a coherent, analysis-ready dataset instead of a pile of technical tables.
  • 2Extract with Azure Data Factory V2Scheduled ADF pipelines connect to those views and pull the data on a defined cadence, handling datasets of up to a million rows per run.
  • 3Transform into report-ready datasetsThe extracted data is shaped to match how the business actually reads it — applying the joins, aggregations and business rules that turn source records into reporting output.
  • 4Load into ADLS Gen2Transformed output is written into the appropriate zone of the data lake, where it is governed and retained as the single trusted source for consumption.
  • 5Serve through Power BIReports and dashboards read from the curated layer rather than connecting back to SAP directly — so reporting load never touches the transactional system, and every report resolves to the same governed dataset.

The design decision that mattered

Instead of building one pipeline per source, I built a small set of generic, parameterized pipelines driven by metadata. Which source, which CDS view, which mappings and which destination are all held as configuration — the pipeline reads that configuration at runtime and executes accordingly.

Before

New source → new pipeline built by hand, with client and table names hardcoded inside it. Logic duplicated across every pipeline; object count grows without limit.

→
After

New source → new metadata entry. One framework serves every source, so logic is fixed in one place and the pipeline estate stops multiplying.

The practical payoff was threefold: onboarding time for a new source dropped by up to 60%, hardcoded client and table dependencies disappeared, and because the framework kept the pipeline footprint small, the platform stayed within its existing licensing tier — avoiding an upgrade cost entirely.

Data Governance

Zone-Based Data Lake with Access Governance

The storage and security foundation the pipelines land into: a layered ADLS Gen2 lake that separates as-ingested data from transformed and report-ready data, secured with Microsoft Entra ID RBAC combined with POSIX ACLs so each team reaches exactly the data it should. Bringing the design and operation in-house removed external vendor support costs — approximately 10M JPY in savings.

ADLS Gen2 Entra ID · RBAC POSIX ACLs
View detailsHide details▼

The problem

Once SAP and internal system data began flowing into the lake at volume, two questions needed answering before it could be trusted as a platform: where does data live at each stage of its life, and who is allowed to see it? Without a deliberate answer, a data lake accumulates into a swamp — files in ad-hoc locations, no distinction between raw and trusted data, and access granted far too broadly because it is the easy option.

Lake zones & access control
Raw zoneExactly as extracted from source — immutable landing
→
Refined zoneCleansed & conformed working data
→
Curated zoneReport-ready datasets served to Power BI
Access layer — Entra ID RBAC at the storage and container level, POSIX ACLs at the directory level

How it is structured

  • Zone separation. Data moves through distinct zones as it earns trust — landed exactly as extracted, then cleansed and conformed, then curated into the report-ready form consumers query. Anyone reading from the lake knows what guarantees the data carries purely from where it sits.
  • Two-layer access model. Entra ID RBAC governs who can reach the storage account and its containers; POSIX ACLs apply fine-grained permissions down at the directory level. Coarse control establishes the boundary, fine control decides precisely which folders a team touches.
  • Predictable paths. A consistent directory convention means the ADF framework writes to a location derivable from metadata, rather than one configured by hand per pipeline — the storage design and the pipeline design reinforce each other.
  • Least privilege by default. Read access to curated output is not the same as write access to raw landing zones; the model separates the two rather than granting broad access for convenience.

Trusted zonesClear separation of raw vs. report-ready

The cost saving came from capability rather than negotiation: once the architecture was designed and operated internally, the external support arrangement it had depended on was no longer needed.
